# Lambda Vision LLM Context Map — Lab Service v0.4.1

This file is intentionally generated by the updater so future LLM agents can load a focused context set instead of reading the entire codebase.

## Scope of this update

Version **v0.4.1** changes Lab Service management and testing UX without coupling Lab Services to Dataset Builder, Sampling LAB, Sequencer, or Agentic Engine yet.

Key semantics:

- Multiple Lab Services may be deployed and active at the same time.
- Deploying **without** `service_id` creates a new independent service ID.
- Deploying **with** `service_id` creates a new immutable version of that same service and makes it active.
- Editing a deployed service loads its pipeline snapshot back into Image Processing LAB.
- `Update Service` publishes a new version; it does not overwrite historical versions.
- `/labs` renders every deployed service as an independent compact manual-run card.
- Output images are fetched only when the user presses a `View <output>` button.
- The large output viewer still uses `ZoomPanImageView`, so zoom/pan behavior is shared with Image Processing LAB.

## Frontend files

### `src/Pages/LabView.tsx`

Purpose:
- Vision LAB launcher.
- Lists all active Lab Services simultaneously.
- Renders one compact `LabServiceCard` per service.
- Each card owns its own test input image and run state.
- `Edit` navigates to `/labs/image-processing?editService=<service_id>`.
- `View <output>` lazily fetches one output preview and opens a large modal viewer.

Important future integration point:
- This page is a UI consumer of the public Lab Service API. Future Sampling/Dataset/Sequencer integrations should not depend on this React component.

### `src/Pages/ImageProcessingLabPage.tsx`

Purpose:
- Main Image Processing LAB page.
- Reads `editService` from URL query parameters.
- Passes that ID into `useImageLabController()`.
- Displays Live/Manual execution controls.
- Displays Lab Service deploy/edit controls.

Service actions:
- `Deploy New Service`: new independent `service_id`.
- `Update Service`: same `service_id`, new version.
- `Save As New`: current stack/checkpoints become another independent service.
- `New Draft`: detaches editor from the current deployed service while retaining stack/checkpoints.

### `src/components/VisionLabs/ImageProcessing/useImageLabController.ts`

Purpose:
- Owns Image Processing LAB editor state and backend session.
- Owns Live/Manual execution semantics.
- Owns Lab Service draft state: name, bound service ID/version, exposed outputs.
- Loads an existing service snapshot when `editServiceId` is supplied.
- Converts service `pipeline_snapshot.nodes` back into `StackOperatorInstance[]`.
- Restores exposed output checkpoint bindings from the service contract.
- Publishes new services or new versions through `LabServiceAPI.deploy()`.

Important service-edit rule:
- Changing a service name no longer detaches from the service ID.
- Explicit `Save As New` / `New Draft` controls identity changes.

### `src/components/VisionLabs/ImageProcessing/ProcessingStack.tsx`

Purpose:
- Stack editor UI.
- In Lab Service mode, exposes a node output as a named service checkpoint/output.
- Not changed by v0.4.1, but it is essential context for service output selection.

### `src/components/VisionLabs/ImageProcessing/types.ts`

Purpose:
- Shared Image LAB TypeScript types.
- Contains `StackOperatorInstance`, `ImagePipelineDefinition`, `ImageLabExecutionMode`, and `LabServiceOutputSelection`.

### `src/api/labServiceApi.ts`

Purpose:
- REST adapter for `/api/v1/lab-services`.
- Defines frontend `LabServiceDefinition` and `LabServiceRunManifest`.
- `deploy()` handles both create-new and create-new-version semantics based on `service_id`.
- `runImage()` invokes the manual runner.
- `outputPreview()` fetches one run artifact for display.

## Backend files

### `app/services/vision_labs/service/models.py`

Purpose:
- Stable service contract models.
- `LabServiceDefinition` contains service identity, version, lab type, input/output contract, and immutable pipeline snapshot.
- `LabServiceOutputBinding` maps a public output name to an internal node/port.

### `app/services/vision_labs/service/repository.py`

Purpose:
- Persistent versioned service storage.
- Active services live under `storage/vision_labs/services/<service_id>/active.json`.
- Historical versions use `vNNNN.json`.

v0.4.1 identity rule:
- `service_id is None` -> `_allocate_service_id(name)` creates a new unique service (suffixes `-2`, `-3`, ... if necessary).
- explicit `service_id` -> `_next_version(service_id)` publishes another version of that service.

### `app/services/vision_labs/service/runtime.py`

Purpose:
- Generic callable runtime entry point: `LabServiceRuntime.run(service, inputs)`.
- Today has an Image Processing adapter.
- Prunes the image pipeline to ancestors required by exposed outputs.
- This is the intended future integration point for Sampling LAB, Dataset Builder, Sequencer, and Agentic Engine.

Do not make future internal modules HTTP-call localhost if they live in the same backend process; call this runtime/service layer directly.

### `app/api/v1/endpoints/lab_service_api.py`

Purpose:
- HTTP adapter around repository/runtime.
- Lists all active services.
- Deploys new services or versions.
- Reads a service/version.
- Manually runs a service with an image.
- Serves output previews from the run store.

### `app/services/vision_labs/service/__init__.py`

Purpose:
- Exposes singleton repository/runtime/run-store objects and service models to API consumers.

### `tests/vision_labs/test_lab_service_core.py`

Purpose:
- Regression tests for service repository/versioning/runtime.
- v0.4.1 explicitly tests that two services with the same display name can coexist with different IDs.
- Tests that editing/publishing with an explicit service ID increments only that service's version.
